\section{Reproduzierbarkeit der Experimente}
\label{sec:appendix-reproducibility}

Die in Abschnitt~\ref{sub-sec:lps-experimente} und Abschnitt~\ref{sub-sec:alps-experimentelle-evaluation} beschriebenen Experimente sind reproduzierbar, indem die benötigten Docker-Images geladen, eigene Konfigurationsdateien erstellt und die Simulationen anschließend gestartet werden.

\subsection{Voraussetzungen}

\begin{itemize}
  \item Installiertes Docker~\citep{docker_2023}.
  \item Installiertes Docker Compose~\citep{docker_compose}.
\end{itemize}

\subsection{Docker-Images vorbereiten}

Die folgenden Befehle bauen bzw. laden alle benötigten Docker-Images im Root-Verzeichnis.

\begin{bashcode}[title={Docker-Images bauen}]
# Simulation-Runner, Kernkomponenten von ALPS (ALP I, ALP II)
# und Hilfsservices (Alarmanlagen-Simulator, Server-Simulator, Validator, TCP-Proxy)
docker build -t lps-rs:0.1.0 -f lps-rust/Dockerfile lps-rust

# ALP Dedup
docker build -t lps-gleam:0.1.0 -f lps-gleam/lps_3/Dockerfile lps-gleam/lps_3

# Auswertungsskripte zur Plot-Erzeugung
docker build -t lps-scripts:0.1.0 -f scripts/Dockerfile scripts

# Kernkomponenten von LPS (LP I, LP II) und Vertreter der Legacy-Services
# (SRV 1 PROXY, SRV 2 PROXY)
docker build -t lps-mqtt-python:0.1.0 -f legacy-proxy-system-docker/Dockerfile.python legacy-proxy-system
\end{bashcode}

\begin{bashcode}[title={Docker-Images bauen}]
# HiveMQ-Broker mit den verwendeten Plugins
docker build -t lps-mqtt-hivemq:0.1.0 -f legacy-proxy-system-docker/Dockerfile.hivemq legacy-proxy-system
\end{bashcode}


\begin{bashcode}[title={Docker-Images laden}]
# RabbitMQ-Broker
docker pull rabbitmq:4.3.6-management

# Mosquitto-Broker
docker pull eclipse-mosquitto:2.1.2-alpine
\end{bashcode}

\subsection{Konfigurationsdateien anlegen}

Vor dem Start der Experimente werden die benötigten Konfigurationen als \gls{yaml}-Dateien angelegt. Diese Dateien enthalten die Parameter für Last, Fehlerbedingungen und Laufzeit der Experimente. Eine Konfigurationsdatei besteht aus einem allgemeinen Teil und einem szenariospezifischen Teil, entweder für \gls{alps} oder für \gls{lps}. Parameter, die mit \texttt{(optional)} gekennzeichnet sind, können weggelassen werden. Fehlerraten werden als Wahrscheinlichkeit zwischen \texttt{0} und \texttt{1} angegeben. Zeitwerte werden als Dauer angegeben, z.\,B.~\texttt{500ms} oder \texttt{10s}.

\begin{yamlcode}[title={Allgemeiner Teil}]
# Zielverzeichnis der erzeugten Simulationsartefakte
simulation_dir: "simulation"
# Externes Docker-Netzwerk, in dem die Services gestartet werden
simulation_docker_network: "lps-simulation-net"

# Image für Simulation-Runner, Kernkomponenten von ALPS und Hilfsservices
lps_rust_image: "lps-rs:0.1.0"
# Image für die Auswertungsskripte
lps_scripts_image: "lps-scripts:0.1.0"
# Image für ALP Dedup
lps_gleam_image: "lps-gleam:0.1.0"
# Image für die Kernkomponenten von LPS
lps_mqtt_python_image: "lps-mqtt-python:0.1.0"
# Image für den HiveMQ-Broker
lps_mqtt_hivemq_image: "lps-mqtt-hivemq:0.1.0"

# (optional) Seed des Pseudozufallszahlengenerators
seed: 1
\end{yamlcode}

\newpage

\begin{yamlcode}[title={Allgemeiner Teil}]
# Simulierte Alarmanlagen
devices:
  # Anzahl simulierter Alarmanlagen
  devices_count: 100
  # Maximales Intervall zwischen zwei Alarmmeldungen pro Alarmanlage
  max_event_interval: 500ms
  # (optional) Minimales Intervall zwischen zwei Alarmmeldungen
  min_event_interval: 100ms
  # Maximale Anzahl erzeugter Alarmmeldungen pro Alarmanlage
  max_events: 100
  # Wartezeit bis zum erneuten Sendeversuch nach einem Fehler
  retry_duration: 500ms
  # Wartezeit bis zum ersten Sendeversuch nach dem Start der Simulation
  wait_before_start: 3s
\end{yamlcode}

\begin{yamlcode}[title={Allgemeiner Teil}]
# Server-Simulator
server:
  # Adresse, unter der der Server-Simulator erreichbar ist
  socket_addr: "0.0.0.0:3000"

  # (optional) Aktiviert ALP Dedup
  deduplication: true
  # (optional) Server beendet sich nach dieser Server-Idle-Zeit, wenn keine Requests mehr eintreffen
  shutdown_after_idle_duration: 30s

  # Zufallsbasiertes Verhalten (ignoriert bei use_gs_prod_workload: true)

  # Wahrscheinlichkeit für negative Antworten
  failure_rate: 0.1
  # (optional) Maximale Verarbeitungszeit eines Requests
  max_work_duration: 50ms
  # (optional) Minimale Verarbeitungszeit eines Requests
  min_work_duration: 10ms
  # (optional) Maximale zusätzliche Antwortverzögerung
  max_response_duration: 50ms
  # (optional) Minimale zusätzliche Antwortverzögerung
  min_response_duration: 10ms

  # (optional) Verarbeitungszeiten werden vom Vorhersagemodell bestimmt
  use_gs_prod_workload: false
  # (optional) Hintergrundlast in Requests pro Sekunde
  # (nur wirksam bei use_gs_prod_workload: true)
  background_load_per_second: 10.0
\end{yamlcode}

\subsection{Simulationen starten}

Vor dem Start wird ein Docker-Netzwerk angelegt, über das die Komponenten miteinander kommunizieren.

\begin{bashcode}[title={Docker-Netzwerk erstellen}]
docker network create lps-simulation-net
\end{bashcode}

Die Simulationen werden aus dem Verzeichnis gestartet, in dem die Konfigurationsdateien liegen.

\begin{bashcode}[title={ALPS-Simulation starten}]
docker run --rm -it \
-v /var/run/docker.sock:/var/run/docker.sock \
-v "$(pwd):/app" \
    jadkhaddad/lps-rs \
    simulation-runner \
    --config-file <amqp-config.yaml> \
    --root-abs-path $(pwd)
\end{bashcode}

\begin{bashcode}[title={LPS-Simulation starten}]
docker run --rm -it \
-v /var/run/docker.sock:/var/run/docker.sock \
-v "$(pwd):/app" \
    jadkhaddad/lps-rs \
    mqtt-simulation-runner \
    --config-file <mqtt-config.yaml> \
    --root-abs-path $(pwd)
\end{bashcode}

\subsection{Ergebnisse}

Nach Abschluss eines Durchlaufs befinden sich die erzeugten Ergebnisse im Verzeichnis  \texttt{\$(pwd)/<simulation\_dir>/mount}
